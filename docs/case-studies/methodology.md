# 검증 방법론 (익명 공개판)

> **공개 정책:** 이 문서는 도구 측정값과 비식별 분류만 기록한다. 개별 보안 판정과 근거는 내부 원본에만 보존하며, 공개판은 취약점 확정이나 대상 식별 자료가 아니다.

## 1. 목적

1. `kkomkkom`이 실제 공개 Next.js 프로젝트에서 빌드·검사·측정을 끝까지 수행하는지 확인한다.
2. 경고와 실패를 재현 가능한 측정값과 비식별 분류로 남긴다.

"취약점을 많이 찾았다"가 목적이 아니다. 개별 보안 판정은 내부 원본에서만 다룬다.

## 2. 대상 선정

공개되어 있고 구조가 서로 다른 Next.js 프로젝트 5개를 골랐다. 공개 문서에서는 Project A–E로만 부른다.

선정 기준은 (a) 공개 저장소, (b) 실제 프로덕션 빌드가 가능한 프로젝트, (c) 서로 다른 라우터·인증·패키지 관리자, (d) Next 14–16 세대를 모두 포함하는 것이다. 스타 수나 인지도는 기준이 아니다.

실제 이름·주소·커밋 SHA·매핑은 내부 자료에만 있다. 공개 문서에는 비식별 검증 식별자만 둔다.

## 3. 격리와 환경

- 저장소 밖 `$WORK`에서 진행했다. 저장소 안에는 공개용 보고서만 둔다.
- 각 프로젝트를 깊이 1로 복제하고, 검증 시점과 기준을 내부에 기록했다.
- `HOME=$WORK/home`으로 npm/pnpm/yarn 캐시를 사용자 전역과 분리했다.
- `CI=1`, `NEXT_TELEMETRY_DISABLED=1`을 공통으로 두었다.
- Node는 v20.20.2, v22.23.2, v26.10.0을 프로젝트에 맞춰 사용했다.
- 검증은 Linux(WSL2), 12 vCPU, 5 GiB RAM, 4 GiB swap에서 수행했다. 빌드는 메모리 사용이 커서 순차 실행했다.

## 4. 설치 정책

- npm은 `npm ci --ignore-scripts --no-audit --no-fund`를 우선했다.
- pnpm은 `--frozen-lockfile --ignore-scripts`.
- Yarn 3은 `--immutable --mode=skip-build`(Yarn 3에 `--ignore-scripts`가 없음).
- **설치·빌드 스크립트의 사전 검토 기록은 보존되어 있지 않으며, 검토의 충분성은 검증되지 않았다.** `npm ci --ignore-scripts`는 설치 스크립트를 건너뛴다는 뜻이지, 프로젝트의 `npm run build` 자체가 안전하다는 증거가 아니다.
- 전역 설치, `npm install -g`, 저장소 설정 변경은 하지 않았다.

## 5. 최초 5개 검사

1. 저장소·커밋·라이선스·Next/Node 버전 확인(내부 기록).
2. 격리 설치.
3. 프로덕션 빌드 성공 확인.
4. `kkomkkom --json` 전체 검사(빌드 재수행 + 페이지 무게 측정).
5. `kkomkkom --fast --json`(빌드 생략, 라우트·페이지·정적 분석).
6. `kkomkkom --artifacts --strict --json`(정적 산출물).
7. 경고/실패 경로를 소스와 대조(개별 판정은 내부).
8. 페이지 무게·coverage·오탐·환경 실패를 표로 정리.

전체 검사는 non-strict로 실행해 `exitCode 0`을 확인했다. `--strict`는 경고/미완료를 실패로 바꾸므로 artifact 실행에만 적용했다.

## 6. 판정 기준

내부에서는 경고를 다음 다섯 가지로 나눴다.

| 분류 | 의미 |
|---|---|
| 실제 문제 | 소스/HTTP로 확인된 인증·민감정보·상태 코드 문제 |
| 의도된 공개 | 프로젝트 문서/설계상 인증이 없는 것이 정상 |
| 오탐 | 도구가 인증/쓰기를 잘못 해석 |
| 도구 한계 | 검사 불가/측정 불가를 `unsupported`/`failed`로 기록 |
| 환경 실패 | 격리 환경에 외부 서비스/비밀번호/소켓이 없어 발생 |

공개판은 사례별 분류 결과를 싣지 않는다. 개별 판정과 근거는 내부 원본에만 있다.

## 7. 후속 검증 (B)

최초 5개 검사 뒤 B에서만 다음을 추가로 확인했다. 원본 5개 결과와 섞지 않고 별도로 기록한다.

### 7.1 범위 축소 기준선

- 샘플이 없거나 필수 쿼리 때문에 GET 400이 나는 스트림·프록시 계열 4개 패턴을 `ignoreRoutes`로 명시 제외했다.
- 그 상태에서 `--update`로 기준선을 만들었다. `coverage: complete`(checked 20, ignored 8, static-only 7, failed 0, unsupported 0), `firstRun:true`.
- 제외 4개와 기존 finding은 그대로다. **complete는 검사 실행 범위를 뜻하며 보안 통과가 아니다.**

### 7.2 무변경 비교

- 같은 조건에서 `--json`을 다시 실행해 `firstRun:false`, `deltaBytes:0`, 4페이지 모두 `comparable:true`를 확인했다.
- 최초 보고서의 페이지 수치와 일부 바이트 차이가 있어, 원본 수치는 덮어쓰지 않고 후속 표에만 기록했다.

### 7.3 합성 클라이언트 증가

- 홈페이지 클라이언트 컴포넌트에서 실제로 참조하는 결정적 고엔트로피 문자열 500,000자를 추가했다.
- 문자열이 tree-shaking·상수 접기로 사라지지 않도록 런타임 DOM 값을 인덱스로 사용해 일부를 참조했다.
- 외부 의존성·외부 서비스 호출은 추가하지 않았다.
- `--json` 재실행에서 기준선 파일의 바이트·SHA가 변하지 않았고, `/`가 `comparable:true`, `heavy:true`, `deltaBytes` 500,119, `deltaPercent` 55.36%, 양쪽 method `manifest-file`임을 assert로 확인했다.
- 이는 **합성 JS 증가 탐지 실험**이다. 실제 취약점, 전송량, 성능 회귀가 아니다. 합성 문자열이 공유 청크에 들어가 4개 페이지가 모두 같은 양만큼 증가했다.

### 7.4 인증 HTTP

- 빌드된 서버를 loopback에만 띄우고, 임시 비밀번호를 메모리에서만 사용했다. 인증 관련 원문은 출력·저장하지 않았다.
- 외부 검색·게시·쓰기 요청은 보내지 않았다.
- **17검사 중 16통과, 1추가검토.** 추가검토 항목의 근거는 내부 원본에만 있으며, 보안 명세 검증 전이므로 취약점 확정으로 승격하지 않는다.

## 8. 증거와 공개 범위

- 원본 JSON·빌드 로그·시간/RSS 로그는 저장소 밖 내부 자료에만 있다.
- 공개용 `logs/results.json`은 경로·비밀값·대상 이름 없이 라우트/상태/수치만 남긴 파생 집계다.
- 공개 문서의 수치와 분류는 내부 원본과 대조했다. 실제 이름·주소·SHA·고유 경로와 민감한 내부 상세는 내부에만 있다.
- 이 보고서는 외부 도입·추천·보안 보증 자료가 아니다.

## 9. 변경 경계

- 꼼꼼 제품 코드·설정·의존성과 원격 upstream은 수정하지 않았다.
- 최초 5개 복제 소스는 수정하지 않았다.
- 후속 disposable clone에서만 검사 범위 설정과 합성 payload를 추가했다가 삭제했다. 이는 최신 코드 동결 지시 전에 수행한 별도 실험이다.
- 커밋, 푸시, PR, 이슈 생성, 배포, npm publish는 하지 않았다.

## 10. 하지 않은 것

- 제품 코드·설정·의존성 버전 수정.
- 실제 배포, npm publish, 저장소 공개 전환.
- 부하 테스트, 퍼징, 실제 공격 시도.
- Windows/macOS, Docker/Kubernetes, 실제 외부 인증·DB 연동.
- 최초 5개 프로젝트의 기준선 저장과 회귀 비교(후속 B에서만 수행).
- 모든 라우트의 수동 POST/PUT/DELETE 실행.
- 유효한 외부 검색·게시·쓰기 요청.

이 범위를 넘는 결론은 내리지 않았다.
